# mirror-init

You are a project-conventions analyst. Analyze the current repository (any language, any stack) and generate AI coding rules — plus optional zero-token local scaffolding — grounded in patterns that actually exist in the code. Never invent conventions the code does not demonstrate.

Execution order: Scope → Analyze → Rules → Slash commands → Scaffolding → Report. Each step feeds the next; do not skip ahead.

## Artifacts

| Artifact | Purpose |
|----------|---------|
| `AGENTS.md` | Canonical rules file — the open standard read natively by Cursor, GitHub Copilot, Codex, Zed, and most AI tools |
| `CLAUDE.md` | One line importing `AGENTS.md` for Claude Code |
| `.claude/commands/<pattern>.md` | One slash command per high-value pattern |
| `plopfile.js` + `.mirrorai/templates/` | Local scaffolding via plop (opt-in) |

**Single source of truth**: rules content lives only in `AGENTS.md`. If the user asks for tool-specific rule files (`.cursor/rules/`, `.windsurf/rules/`, `.clinerules`, `.github/copilot-instructions.md`), emit a thin stub that points to `AGENTS.md` — never duplicate the content.

**Ownership marker**: every file mirrorai writes starts with a marker on line 1 — `<!-- mirrorai:generated -->` in Markdown, `# mirrorai:generated` elsewhere. A detected file without its marker is user-authored: never modify it without asking, per file:

> `<file>` exists but wasn't generated by mirrorai. (m)erge — keep your content, append mirrorai's sections / (o)verwrite / (s)kip

## Step 1 — Scope the run

Detect existing artifacts from the table above (including `plopfile.{js,mjs,cjs}`).

**First run** (none exist): ask one question — *"Also generate a plopfile and templates for zero-token local scaffolding? (y/n)"* — then proceed.

**Re-run** (any exist): list the detected files annotated `[mirrorai]` or `[user-authored ⚠️]` from the marker check. Derive the previously generated pattern list (union of marker-bearing `.claude/commands/*.md` filename stems excluding `mirror-init`, and `plop.setGenerator('<name>', …)` entries). Then ask:

- **a. Refresh everything** (default) — regenerate all mirrorai-owned artifacts from a fresh analysis
- **b. Refresh selected patterns** — user enters comma-separated pattern names; regenerate only those patterns' slash commands and plop generators/templates (preserving other generators in the plopfile); leave `AGENTS.md` / `CLAUDE.md` untouched
- **c. Start over** — re-ask the scaffolding question, delete mirrorai-owned artifacts excluded by the new answer (e.g. plopfile and templates if scaffolding is now declined), then regenerate everything from the fresh analysis

Hide option b when the pattern list is empty. Every choice still runs the full analysis below — output accuracy depends on it. For option b, restrict pattern selection in Step 2.5 to exactly the chosen names.

## Step 2 — Analyze

1. **Stack** — identify the language/ecosystem from root manifests (`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`/`build.gradle`, `composer.json`, `Gemfile`, `*.csproj`, `Package.swift`, `pubspec.yaml`, `mix.exs`, …) and the framework plus core libraries from the dependency list. If multiple manifests indicate a monorepo or polyglot project, ask which subproject to analyze.

2. **Layout** — record the real directory structure: source roots, module organization (feature-based / layered / flat), test locations, entry points. Assume no fixed names.

3. **Core abstractions and infrastructure** — find the wrappers business code actually goes through: routing/controllers, data access, state management, error handling, auth, logging, config, caching, queues. For each, record location, usage convention, and anything that must not be bypassed.

4. **Cluster** — classify every business file by unit type (list page, form page, CRUD endpoint, scheduled job, message consumer, CLI command, mobile screen, …) from its imports, structure, and naming. On large repositories (roughly > 300 business files), classify from paths, names, and import lines alone — do not read every file. Group files by type and read 1–3 representatives per group in full to extract the shared structure.

5. **Qualify patterns** — a cluster is a high-value pattern only if it has **≥ 3 instances**, **≥ 50 average lines**, and **≥ 80% structural similarity**. Rank survivors by frequency, size, similarity, and how many coordinated files each instance touches (routes, tests, migrations); keep the **top 3–6**. Name each `new-<semantic>` in kebab-case using the project's own vocabulary (`new-approval`, `new-pipeline`, `new-resource`) — never generic placeholders.

6. **Resolve style generations** — in mature codebases, conventions coexist in generations. When a cluster splits into distinct styles, pick the canonical one by momentum: check `git log` to see which instances are actively maintained, and treat the dominant recently-touched style as the convention. Never average styles together. Representatives, reference files, and template seeds (Step 5) must all come from the canonical style; record superseded styles for the report's ⚠️ Issues section. If no style dominates, exclude the cluster and flag it.

**Edge cases**: fewer than 3 business files, or no qualifying cluster → write `AGENTS.md` with general constraints only and skip Steps 4–5.

## Step 3 — Write the rules

`AGENTS.md` — marker on line 1, then the sections below. Every line must come from the actual code: cite real file paths, name real wrappers, state concrete reasons. No boilerplate, no "be careful with X". Target ≤ 150 lines.

**Wrap every cited file path in backticks** (`` `src/lib/db.ts` ``) — in `AGENTS.md` and in every slash command file. `npx mirrorai check` parses backtick-wrapped paths to detect stale rules in CI; an unwrapped path is invisible to it.

```markdown
<!-- mirrorai:generated -->
# Project Conventions

## Stack            — languages, frameworks, core libraries, versions
## Layout           — each top-level directory and its purpose
## Core Abstractions — each wrapper: location, usage, what must not be bypassed (and the correct replacement)
## Infrastructure   — each shared facility with a usage example
## Code Style       — naming, import order, typing/comment requirements, formatter/linter config location
## Testing          — framework, file organization, naming convention
## Prohibited       — concrete rules discovered from the code, each with its reason
## Reference Files  — per unit type, the best file to read before writing new code
## Patterns         — auto-apply rules, one per high-value pattern:
   trigger keywords → reference file → constraints → side effects (tests, routes, docs)
   → scaffold hint: run `npx mirrorai new <pattern> <name>` first, then fill in business logic
```

**Verify before finishing**: check that every file path cited anywhere in `AGENTS.md` exists on disk. Fix or drop any citation that doesn't resolve — a rule that cannot point at real code does not ship.

`CLAUDE.md`:

```markdown
<!-- mirrorai:generated -->
See @AGENTS.md for project conventions.
```

If a user-authored `CLAUDE.md` exists, the merge option means appending the `@AGENTS.md` import line.

## Step 4 — Slash commands

For each selected pattern, write `.claude/commands/<pattern>.md`:

- marker on line 1, then `# <pattern>` and a one-line description
- **Trigger criteria** — phrases in a user request that should auto-apply this command
- **Code example** — extracted verbatim from the project's canonical instance, no pseudocode
- **Variables** — which fields plop fills from the name, which the AI derives from requirements
- **Side effects** — other files to create or modify (tests, route registration, docs)
- **Flow** — scaffold with `npx mirrorai new <pattern> <name>`, then fill in business logic

On a full run the command files map one-to-one to the selected patterns; on option b, write only the chosen ones and leave the rest untouched.

## Step 5 — Scaffolding (opt-in)

**Format**: `"type": "module"` in root `package.json` → ESM `plopfile.js`; otherwise CJS `plopfile.js`; no root `package.json` → `plopfile.mjs`.

**Generators** — one per pattern, with **exactly one prompt** (the name), so `npx plop <pattern> <name>` runs non-interactively from a single positional argument. Derive any extra values from the name via case helpers (`{{camelCase name}}`, `{{pascalCase name}}`, `{{kebabCase name}}`, `{{snakeCase name}}`, `{{constantCase name}}`). Resolve template paths relative to the plopfile, pointing into `.mirrorai/templates/<pattern>/`.

**Templates** (`.mirrorai/templates/<pattern>/*.hbs`) — extract from the most canonical instance of the pattern (the seed):

- name-derived identifiers, URLs, table names → the matching case helper
- business fields and parameter lists → `TODO` markers for the AI to fill in later
- keep all structural code: imports, decorators/annotations, lifecycle, error handling
- drop one-off logic that isn't part of the shared pattern

Templates always end in `.hbs`; the rendered output can be any language.

**Validation (mandatory)** — run immediately after writing:

1. **Load** — `node --check` the plopfile, then import/require it to catch runtime errors.
2. **Trial-run** — for each generator: record the resolved output paths (plop has no dry-run), then run `npx plop <pattern> __mirrorai_test__`.
3. **Check the output** — file exists at the expected path; no leftover `{{…}}` placeholders; syntax-check when a single-file checker exists (`node --check`, `python -m py_compile`, `ruby -c`, `php -l`, `gofmt -e` — skip compile checks for TS/Rust/Java/C# etc., where isolated files can't compile); structure matches the seed — same imports, same core abstractions, same major sections, line count within ±30%, and none of the seed's concrete business identifiers or API paths.
4. **Clean up** — delete the trial output and any directories the trial created, nothing else.
5. **On failure** — fix and retry, at most twice. A broken plopfile itself must be fixed, never skipped. A generator still failing after retries: remove it and its matching slash command, and record the reason for the report.

## Step 6 — Report

```
✓ mirror-init complete

Stack: <languages / frameworks / core libraries>
Business units (<N> files): <type>: <n>, …

Patterns:
  - <pattern> (<n> instances) → /<pattern> [+ plop generator: passed | repaired | removed (<reason>)]
  (or: no qualifying patterns — AGENTS.md contains general constraints only)

Files written: <actual list>

Next: describe any task normally — the AI applies these rules automatically.
      Catch stale rules in CI with: npx mirrorai check
      Scaffold skeletons with: npx mirrorai new <pattern> <name>   (if plopfile generated)
```

If the analysis surfaced consistency problems (a unit type split across generations of style, abstractions bypassed in places), append a `⚠️ Issues` section naming the canonical style chosen, the files that deviate from it, and a suggested next step.
